# 설계 철학 — LLM 에이전트 규칙의 자산화 (Design Philosophy)

> **강의용 문서.** 본 저장소(kuks_claude_agent_setup)가 왜 이런 모양인지를 처음 보는 사람에게 설명한다.
> 대상: LLM 코딩 에이전트(Claude Code 등)를 실무에 쓰려는 개발자. 예상 강의 시간 60~90분.

---

## 1. 문제 — LLM 에이전트는 어떻게 실패하는가

LLM 에이전트를 실무 프로젝트에 투입하면 다음 실패가 **반복**된다. 본 저장소의 모든 번들은
이 실패 목록에 1:1 로 대응하는 해독제다.

| # | 실패 모드 | 증상 | 대응 번들 |
| --- | --- | --- | --- |
| F1 | **의도 부채** | 사용자 지시가 요약·재해석 과정에서 왜곡되고, 원문은 세션 종료와 함께 증발 | `user_instruction` |
| F2 | **환각·추정** | 매뉴얼·데이터시트를 "기억"으로 답변, 외부 문서 무검증 인용 | `external_reference` |
| F3 | **자기승인** | 자기가 짠 코드를 자기가 "완료·검증됨"으로 선언 | `coding`(never-self-approve), `code_review` |
| F4 | **무기록 재발** | 실수 지적에 "다음부터 잘하겠다"로 종결 → 같은 실수 반복 | `mistake` (closure 강제) |
| F5 | **부채 은닉** | TODO/FIXME 를 뿌려놓고 잊음, 이해 못 한 코드에 침묵 | `debt` (registry + id 강제) |
| F6 | **세션 충돌** | 동시 다중 세션이 같은 트리에서 서로의 미커밋 변경을 커밋·파괴 | `session_workflow`, `git_workflow` |
| F7 | **품질 미검증 산출물** | 다이어그램이 겹치고 글자가 벗어나도 "완료" 선언 | `drawio` (2단 검증) |
| F8 | **즉답 패치** | 버그 원인 진단 없이 증상만 덮는 수정 직행 | `issue_fix` (진단→승인→검증) |
| F9 | **재구현 낙관** | 리버스 엔지니어링 재구현이 "대충 비슷"한데 동일하다고 주장 | `reverse_engineering` (비트 대조) |

**핵심 관찰**: 이 실패들은 모델 성능 문제가 아니라 **프로세스 부재** 문제다. 사람 개발자도
규칙 없이 일하면 같은 실수를 한다. 차이는 사람은 조직의 SOP(Standard Operating
Procedure)·코드리뷰·CI(Continuous Integration)로 묶여 있고, LLM 은 기본 상태에선 아무 것에도
묶여 있지 않다는 것이다. **그래서 LLM 에게도 같은 것을 만들어 준다** — 그것이 본 저장소다.

## 2. 핵심 원칙 6

### 원칙 1 — 규칙은 자산이다 (Rules as Assets)

규칙을 채팅으로 말하면 그 세션에서 죽는다. 규칙을 프로젝트 CLAUDE.md 에 쓰면 그 프로젝트에서
죽는다. 규칙이 살아남으려면 **버전 관리되는 독립 저장소의 설치 가능한 번들**이어야 한다.

- 자산 = 폴더별 **자기완결 번들**: `규칙.md`(SSOT, Single Source of Truth) +
  `claude.snippet.md`(등록 포인터) + `install.sh`(설치기) + `hooks/`(자동 개입) +
  `checks/`(기계 검증) + `domains/`(선택 도메인 규칙)
- 설치는 `install.sh <타깃>` 하나. 루트 중앙 스크립트 없음 — 번들 간 결합도 0.
- 개선은 번들 저장소에 커밋 → 각 프로젝트는 `git pull` + `install.sh --status` + 재실행으로 전파.
  규칙의 **업스트림/다운스트림** 구조: 한 프로젝트에서 배운 교훈이 모든 프로젝트로 흐른다.

### 원칙 2 — 컨텍스트는 비싸다 (Registration Pointer + Lazy Read)

전체 규칙을 CLAUDE.md 에 붙이면 모든 대화의 컨텍스트를 점유하고, 모델은 긴 텍스트 속 규칙을
무시하기 시작한다. 그래서 **2단 구조**를 쓴다:

1. `claude.snippet.md` → 타깃 CLAUDE.md 에는 **트리거 + 포인터 몇 줄**만 등록
   ("X 트리거 감지 시 먼저 docs/claude_guideline/X/X.md 를 Read 한 뒤 따르라")
2. 규칙 본문은 `docs/claude_guideline/<번들>/` 에 설치 — **트리거가 발동했을 때만** 모델이 Read

포인터 문구는 "**응답 전 의무 선행 점검**(등록만 알고 건너뛰지 말 것)"을 명시한다 — 모델이
"그 규칙 알아요"라며 원문 Read 를 생략하는 것 자체가 관찰된 실패 모드이기 때문이다.

### 원칙 3 — 권고는 강제가 아니다 (3-Layer Enforcement)

LLM 에게 "하지 마"라고 쓰는 것은 **권고**일 뿐이다. 본 저장소는 강제 수준을 정직하게 3층으로
분리하고, 각 규칙이 어느 층인지 표기한다:

| 층 | 수단 | 강제력 | 예 |
| --- | --- | --- | --- |
| L1 규칙 텍스트 | `⟦권고⟧` 표기 | 모델의 선의에 의존 | 명명 규칙, 스타일 |
| L2 훅(hook) | SessionStart/UserPromptSubmit 주입, PreToolUse 게이트, PostToolUse 추적 | 세션 안에서 기계 개입 — 그러나 훅 미설치 환경에선 무력 | drawio 규칙 주입, git 4게이트, 세션 파일 추적 |
| L3 CI 이빨 | `⟦CI:<id>⟧` ↔ `checks/<id>.sh` (pre-commit·CI) | **진짜 강제** — 통과 못 하면 커밋·머지가 물리적으로 불가 | drawio-lint, debt-marker, entry-lint |

문서의 `⟦CI:<id>⟧` 마커는 장식이 아니라 **검증 스크립트와 1:1 계약**이다. 마커만 있고
스크립트가 없으면 그 규칙은 이빨 없는 선언이고, 그렇게 정직하게 부른다("이빨").

> **강의 포인트**: 이 3층 구분이 저장소 전체에서 가장 중요한 설계 결정이다. "강제는 CI 만
> 진짜"라는 원칙은 규칙을 특정 도구(Claude Code)에서 떼어내 어디로든(예: GitHub Copilot)
> 이식 가능하게 만든 바로 그 이유이기도 하다 (→ §6).

### 원칙 4 — 검증은 기계 + 눈, 2단이다

기계 린트는 기하·형식 결함을 잡고(L1~L11 사선 화살표·글자 벗어남·박스 겹침 …), 렌더 캡처를
**눈으로 보는** 단계가 디자인·가독성을 잡는다. 기계가 못 지키는 층(Layer B)은 기계가 지킨다고
거짓말하지 않고 "직접 수행하라, 못 했으면 미수행을 산출물에 명시하라"고 쓴다 — **검증 불가를
검증됨으로 위장하지 않는 정직성**이 규칙 문서 전반의 톤이다.

### 원칙 5 — 모든 실패는 파일로 남는다 (Everything Leaves a Record)

| 무엇 | 어디에 | 강제 장치 |
| --- | --- | --- |
| 사용자 지시 원문 | `docs/user_instructions/` (세션별 → 누적 병합) | UserPromptSubmit 훅 자동 기록 |
| Claude 의 실수·규칙 위반 | `docs/claude-mistake/YYYY-MM-DD-NNN.md` | SessionStart 가 미해결 entry 주입, closure 는 `reflected_assets` 1+ 필수, open 7일 시한 |
| 기술·이해·의도 부채 | `docs/debt/registry.md` | 코드 맨 TODO/FIXME 마커는 `⟦CI:debt-marker⟧` 가 커밋 차단 |
| 버그·수정 이력 | `docs/issues_and_fixes/` | issue_fix 사이클 기록 단계 |
| 설계 결정 | `docs/adr/` (ADR, Architecture Decision Record) | coding SOP 사전승인 단계 |
| 설치 상태 | `docs/claude_guideline/INSTALLED.md` | install.sh 가 커밋 해시 기록 → `--status` 드리프트 검출 |

기록은 처벌이 아니라 **재발 방지 자산의 원료**다: mistake entry 의 closure 조건이
"반성문"이 아니라 "`reflected_assets` — 어느 규칙/훅/체크에 반영했는가 1개 이상"인 것이
이 철학의 압축이다. **실수 → 규칙 개정 → 번들 재배포**의 루프가 저장소를 성장시킨다.

### 원칙 6 — 설치는 비파괴·멱등 (Non-destructive, Idempotent)

- 기존 CLAUDE.md·settings.json 은 **덮어쓰지 않고 append/merge**, 마커로 중복 스킵,
  settings.json 은 사전 백업.
- 모든 install.sh 는 **재실행 안전**(멱등) — "업데이트 = 재실행"이라는 단일 절차가 성립한다.
- `INSTALLED.md` 에 번들·설치 커밋·인자를 기록 → `--status` 가 최신/재설치 권장/기록 없음
  3판정 + 로컬 수정(드리프트)도 검출.

## 3. 번들 해부 — 구조 규약

```
<번들>/
├── <번들>.md          # 규칙 SSOT — self-contained, 이것만 읽으면 따를 수 있다
├── claude.snippet.md  # 타깃 CLAUDE.md 에 붙는 등록 포인터 (통파일 설치가 아님)
├── install.sh         # 멱등 설치기 (+ --status 낡음 점검)
├── hooks/             # L2: 세션 자동 개입 (주입·게이트·추적)
├── checks/            # L3: ⟦CI:<id>⟧ 와 1:1 계약된 검증 스크립트
├── domains/           # 선택 도메인 규칙 (ros2·embedded·concurrency …)
└── experiments/       # 번들 자체의 검증 실험 (SIL/HIL)
```

- 규칙은 단순하게, 분석·검증은 분리 — 규칙.md 가 코드를 품지 않는다.
- 도메인 규칙은 코어와 분리 설치(`install.sh <타깃> [도메인...]`) — 필요 없는 프로젝트에
  ROS2(Robot Operating System 2) 규칙을 강요하지 않는다.
- 전역 번들(`acronym`·`computer_use`)만 `~/.claude` 에, 나머지는 프로젝트별 설치.

## 4. 사례 연구 — 강제 계층이 실제로 작동하는 모습

### 4-1. drawio: 강제 3겹

① `hooks/drawio-reminder.py` 가 작성 **전** 규칙을 주입하고 ② `hooks/drawio-write-gate.py` 가
쓴 **직후** 린트를 돌리고 ③ `⟦CI:drawio-lint⟧` pre-commit 이 커밋을 차단한다. 눈 검증(렌더
캡처 검토)은 기계 강제가 불가능하므로 규칙 텍스트가 "미수행이면 미수행이라 적어라"를 요구한다
— 층마다 가능한 최대 강제를 걸되, 불가능한 곳에서 가능한 척하지 않는다.

### 4-2. git_workflow: 스코프 기반 게이트

4개 PreToolUse 게이트(stage/commit/push/tree)의 판정 원칙은 "**다른 세션이 살아있는가**"가
아니라 "**이 명령이 남의 것을 건드리는가**"다. 정당한 동작마다 게이트가 뜨면 사용자는
override 를 반사적으로 붙이게 되고, 그 순간 게이트는 죽는다 — **오탐이 많은 강제는 강제가
아니라는** 운영적 통찰이 버전 1.8.0 의 스코프 기반 재설계로 남아 있다(버전 이력 참조).

### 4-3. mistake: closure 의 강제

실수 기록은 `type` 판정(명시 규칙 위반이면 rule-violation 우선) → entry 파일 → **자산 반영
(`reflected_assets` 1+)** 까지가 한 사이클이다. "기록 없는 다음부터 잘하기 종결 금지"가 규칙
문구 그대로이며, entry 형식은 `checks/entry-lint.sh` 가 검증한다.

## 5. 안티패턴 — 이 저장소가 의도적으로 하지 않는 것

- **중앙 통합 설치기 없음** — 번들 간 의존이 생기는 순간 하나의 실패가 전체 설치를 막는다.
- **규칙 전문을 CLAUDE.md 에 인라인하지 않음** — 컨텍스트 낭비 + 규칙 무시 유발 (원칙 2).
- **자동 default 없음** — git 협업 모드 미선언 시 solo 로 임의 진행하지 않고 **묻는다**.
  모호함을 침묵으로 해소하면 그 결정은 기록되지 않은 채 반복된다.
- **오탐 많은 게이트 없음** — §4-2. 게이트는 정확히 위험한 것만 막아야 신뢰를 유지한다.
- **훅이 조용히 실패하지 않음** — 정리 실패·보류는 반드시 소리내어 보고 (git_workflow §2-1).

## 6. 이식성 — 철학의 최종 시험

3층 강제 모델(원칙 3)의 층위 분리는 도구 독립적이다:

- **L1 규칙 텍스트** — 어떤 에이전트든 markdown 지침을 읽는다 → 이식 대상
- **L2 훅** — Claude Code 고유 기능 → 이식 불가, **대체 필요**
- **L3 CI 이빨** — git·pre-commit·CI 는 도구 무관 → **그대로 이식**

따라서 훅이 없는 도구(예: GitHub Copilot)로 옮길 때 필요한 작업은 "L2 를 L3 로 내리거나
L1 로 올리는 재배치"뿐이며, 규칙 본문(SSOT)은 그대로 산다. 구체 절차는
[copilot/copilot_adaptation.md](../copilot/copilot_adaptation.md) 참조.

## 7. 강의 마무리 — 토론 질문

1. 여러분 팀의 LLM 실패 목록(§1)에는 무엇이 더 있는가? 그 실패의 해독제 번들을 설계한다면?
2. 어떤 규칙을 L1 에서 L3 로 올릴 수 있는가? 올릴 수 없다면 그 이유는 기술 부족인가, 본질적
   불가(눈 검증)인가?
3. "오탐 많은 게이트는 강제가 아니다" — 여러분의 CI 에서 개발자들이 반사적으로 우회하는
   검사는 무엇인가?
4. 실수 기록의 closure 를 "반영된 자산 1+"로 정의하는 것과 "재발 0"으로 정의하는 것의 차이는?
